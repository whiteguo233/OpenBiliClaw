# 桌面启动延迟复测（2026-10-23）

## 结论

上一轮优化解决了封面被状态查询挤进连接队列的问题，但没有解决卡片出现之前的资源加载与初始化开销。本轮减少隐藏设置查询、提前开始鉴权并提前发现脚本资源。八次真实导航交替对照仅显示小幅热启动收益，冷启动没有明显改善；不能据此宣称首访已经流畅，也不能把先后批次的大幅差异当作可靠提升。

## 实现与保护

- `defer` 脚本移到 head，保留全部依赖顺序；仍在 DOM 解析完成后执行，不增加打包依赖。
- 恢复后端地址与前端设置后即开始登录检查，与剩余展示初始化重叠；业务水合仍等待登录成功。
- 隐藏的鉴权／自启动设置不再启动即请求；控件初始禁用，打开设置时读取服务端状态，现有编辑与保存流程保留。
- 不改模型服务、推荐生成、图片来源、Cookie 或用户配置。

## 实验

基线 `f6f4d1e6`，隔离后端端口 18476，真实 API / SQLite / 图片 CDN 请求。数据库使用本机最近的八条真实内容，单独验收推荐记录；不调用推荐模型、不发布评论。macOS Chromium 1440×1000，不等同于用户 Windows Edge 现场。图片已在服务端热缓存；本轮不比较 CDN 冷缓存。每次禁用浏览器缓存的导航后跟一次允许缓存的导航。

先连续测量旧版、按需设置版、再加 head 脚本版，各六轮。旧版热缓存卡片 1108–1468ms，新版 810–830ms，但顺序测量容易受负载与缓存影响。随后用同一后端、浏览器、数据，按 before / after / after / before 切换真实静态文件，完成八次导航；无网络响应拦截。切换后恢复修复文件。保留交替结果作为主要结论：

| 指标，中位数 ms | 基线 | 修复 | 变化 |
| --- | ---: | ---: | --- |
| 浏览器缓存禁用：八张卡片 DOM 出现 | 1419.3 | 1422.4 | 基本不变 |
| 浏览器缓存禁用：首四张图片完成 | 1553.8 | 1615.3 | 慢约 4% |
| 浏览器缓存允许：八张卡片 DOM 出现 | 992.8 | 938.3 | 快约 5.5% |
| 浏览器缓存允许：首四张图片完成 | 1037.1 | 999.3 | 快约 3.6% |

每组每种缓存条件只有两次，样本小且存在波动：一次旧版热导航比新版还快。这是减少请求的功能修复及小幅性能信号，不是统计显著的性能承诺。预设 800ms 卡片目标未达成。

## 剩余原因与下一阶段

基线主脚本约 695KB 原文／171KB gzip，页面同时加载十余个辅助脚本；冷启动主脚本曾等待连接队列 271–465ms，初始化观察到约 100–300ms 的主线程长任务。冷启动还要获取语言目录、检查鉴权和服务健康后才能读推荐。不能仅凭时间线把整个长任务归因于某一个函数。CDN 首次下载在上一轮曾使首四张图片耗时约六秒，本轮缓存命中不覆盖该问题。

直接增加 preload 的诊断试验出现重复请求且没有稳定收益，未保留。更大的改善需要对主脚本做函数级性能采样，再把设置／聊天等非首屏模块拆分为按需加载；本次不在没有回归覆盖的情况下大规模改写单文件应用。

## 验证

新增真实 Chromium 回归首先在基线失败：启动鉴权请求为两次，期望一次。修复后检查首页只做一次鉴权、不读隐藏自启动设置、打开设置恢复读取；另验证登录未完成不请求推荐。

验证：六个桌面回归文件（列表稳定性及 Chromium E2E、后台会话、自动加载、自启动、候选池状态）共 57 项通过；`ruff check src/ tests/`、测试文件 Ruff 格式、`node --check` 与 `git diff --check` 通过。没有合入 main、安装到用户电脑或发版；用户正在运行的旧服务不会自动获得这些更改。
