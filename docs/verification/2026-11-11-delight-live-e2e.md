## 消费、耗尽与页面恢复

1. 控制合格池为两条。真实 `POST /api/delight/sent` 后，队列仍保留原卡，`delight_seen=0`。
2. `POST /api/delight/respond` 的 view 返回 200；独立只读 SQLite 连接确认 `pool_status=shown`、`delight_seen=1`，下一次 GET 补出不同身份，WebSocket 收到 `delight.refreshed`。
3. dismiss 第二条返回 200，队列变为 0；使用同一个 request_id 再次 dismiss 返回 `duplicate=true`。没有重放刚消费的条目。
4. 该副本还保留 16 条 pending_eval 和 4 条 evaluated 素材。因此 raw 库存依次为 **22 → 21 → 20**，而可展示 fresh 内容为 **2 → 1 → 0**。这不是消费未归还库存：归还量准确为 2，剩余 20 条尚未成为可展示内容。
5. 在副本中重新准入一条未消费的真实候选，并在提交后通过实际 event hub 发出补位事件；GET 返回 1 条新身份，raw 为 21。这里只验证真实入池之后的通知与读取，不宣称自动联网补货成功。
6. Chrome 页面展示该单条惊喜；实际点击“看过了，不再推荐”后卡片消失。再准入另一条真实候选，页面通过真实 WebSocket / HTTP 自动显示新卡，未手动刷新。页面正确区分“当前可换 0 条”和“素材整理 20 条”。部分历史封面显示加载失败，本次没有修复或验收外站图片链路。
