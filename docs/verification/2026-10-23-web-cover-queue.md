# 桌面 Web 首屏请求排队优化（2026-10-23）

## 原因与范围

基于 `58d066c6` 创建独立 worktree／分支 `fix/web-cover-request-queue`。在专用 Chromium、隔离 FastAPI（18476）与 8 条已有真实内容副本上复现。图片通过真实 CDN 与图片代理读取，浏览器 HTTP 缓存禁用，热测使用服务端图片缓存；没有启动采集、评论或私信。为使后端处于正常模式，使用本机已有模型配置，不进行模型质量测试。

Resource Timing 显示，推荐返回之后，建卡代码在元素挂入 DOM 之前同步发起每张卡的收藏、稍后再看查询：8 张卡产生 16 个 `/api/saved/*/status` 请求。初始化同时发出十余个辅助请求。图片已经声明高优先级，但发起时同源请求队列已被填满。

三个候选解释为逐卡状态请求、辅助水合突发、主线程渲染。诊断时仅通过浏览器拦截立即返回状态读取，其余实际请求保持不变，图片排队显著下降。这一轮是因果探针，不作为真实全链路验收。最终优化后的测量没有任何请求拦截。

## 修改

- 逐项保存状态读请求移至后续任务，最多两个在途；成功或失败均释放名额。实际保存／取消操作不经过该队列，原有 mutation registry 版本保护保留。
- 辅助水合任务用两个 worker 逐项处理，失败不阻断后续任务；推荐、运行状态和待确认提示仍优先启动。
- 运行状态首次读取完成后即可建立实时连接，不等待辅助面板全部加载完。连接函数原有的幂等、后台暂停和恢复机制保留。
- 没有新后端 API、配置、依赖或安装步骤；推荐算法及服务端图片缓存策略不变。

## 测量

原始路径级时间线（已去掉 URL 参数）见 [timings.json](assets/2026-10-23-web-cover-queue/timings.json)。每个阶段连续三次导航，固定取后两次的前四张缓存图片请求；样本很小，不能当作生产 P95 或 Windows 网络保证。前后均非并行 pytest 负载下测量。

| 阶段 | 图片排队中位数 | 图片请求总耗时中位数 |
| --- | ---: | ---: |
| 修复前 | 798.5ms | 990.5ms |
| 只限制逐卡状态读取 | 364.5ms | 522.5ms |
| 再限制辅助水合（实时连接调整前） | 3.5ms | 806ms |
| 最终版本（含实时连接提前启动） | 4ms | 139ms |

早期第三阶段从导航到前四张图片完成分别约 2.33、3.46、2.20 秒。整体启动仍受脚本、其他接口和机器负载影响，不能把单张图片请求时间宣称为整页加载时间。冷 CDN 下载、惊喜推荐头图和用户 Windows 环境不在此次性能结论范围内。

## 回归

新增实际页面建卡测试：24 张卡不能在 DOM 挂载前发出 48 个状态请求；在两个请求悬挂时并发仍有界，释放后所有按钮更新正确；首个请求失败也能继续排空。旧实现曾明确出现 `status reads flooded the connection queue: 48`。

另一个测试阻塞两个辅助列表，验证推荐卡片与实时连接仍可用；释放时令一个列表失败，后续配置加载仍执行。已有列表节点、滚动位置、后台恢复、降级与收藏操作契约同时复测。

初次扩展回归发现旧测试在实时连接未建立时直接注入事件，报 `no live runtime socket`。修复实时连接等待辅助水合的问题，并让事件注入显式等待连接就绪；不是绕过列表稳定性断言。测试环境系统 Chrome 启动不稳定，浏览器测试通过临时 runner 选择本机已安装的 Chromium for Testing，不改项目的浏览器依赖。

最终相关回归：`pytest tests/test_desktop_web_list_stability_e2e.py tests/test_desktop_web_pool_status.py tests/test_desktop_web_background_session.py tests/test_desktop_web_saved_card_actions.py tests/test_desktop_web_degraded_recovery.py -q`：**51 passed，102.65s**（上述临时 Chromium runner）。`ruff check src/ tests/`、`node --check .../app.js`、`git diff --check` 均通过。本次未修改 Python 生产代码或类型接口，没有重复跑 MyPy 或全仓测试。

最终版本再次连续三次真实导航，前四张图片完成时间分别约 **1.91、1.95、2.08 秒**；修复前后两轮热加载为 3.58、3.99 秒。请求排队明显降低，但样本和环境有限，仍不做普遍整页性能保证。最终恢复测试环境，关闭专用浏览器和 API，删除临时模型配置、内容副本及日志；主工作区未修改，未合入或发布。
