# 保持推荐流程的重复计算优化（2026-09-08）

## 范围与约束

基线为后端 main `ac942817`，实现分支为 `perf/recommendation-snapshot-reuse`。没有修改候选数量、准入阈值、Curator 权重、平台补位、MMR 公式及权重、主题/风格/兴趣放大上限、补满策略、语义向量缺失策略、文案读取或 shown 原子提交。比较要求为：给定同样输入，返回同样条目且顺序完全一致。

改动只复用已经计算过的结果：

1. 同一 MMR 选择调用内，每对向量的余弦值最多计算一次，包括结果为零的情况。仍调用原 `cosine_similarity`，不换近似算法或浮点实现；批次结束即丢弃。
2. 同一隔离读取事务内，相同连接、SQL 和参数的候选原始查询行只读取一次。后续每次仍执行时间有效性、已看、链接可用性过滤和对应 topic window，不缓存过滤结果；事务关闭时清空，下一次请求重读。
3. 独立库存状态读取也使用只读事务，复用事务内动态阈值与原始查询行，避免同一状态统计多次重算历史阈值。完整候选过滤和统计字段保留。

## 固定输入对照

对实际数据库做 SQLite backup，随后只在副本上初始化、读状态和重放。向量缓存以只读方式打开，不发模型请求、不消费线上候选。存储重放使用 Database 默认准入策略；历史重放取已分类且有文案的最近记录及每个文本最后访问的缓存向量，属于算法对照，不代表当前生产 namespace 和库存的完整复现。

每项交替执行优化前后各 8 次，丢弃首轮取中位数。第一轮结果：

| --- | ---: | ---: | --- |

| 独立库存状态读取 | 362.90ms | 165.18ms | 所有字段一致 |

| MMR：80 条真实历史候选，768 维向量全覆盖，取 10 条 | 513.75ms | 68.45ms | 条目和顺序一致 |

另有 48 组固定随机种子边界场景，覆盖不同窗口/批次大小、同分、主题/风格集中、部分向量缺失、零向量、正负 bonus 与 amplification guard；优化前后条目顺序全部一致。

同时运行回归测试时再次执行脚本，40/80 条 MMR 分别为 278.72 → 46.80ms、694.55 → 92.67ms；绝对耗时随机器负载变化，输出仍一致。原始聚合结果：[普通负载](results/recommendation-reuse-normal.json)、[回归测试并行负载](results/recommendation-reuse-regression-load.json)。阶段时间不能相加后当成实际手机端请求延迟，也不承诺所有换批都小于某个固定秒数。

## 回归验证

新增回归覆盖：每对余弦每批只算一次且下一批重算；SQL 每个事务只查一次而每次过滤仍执行；topic window 不同仍得到不同正确数量；下一事务看见 shown 提交；异常路径清空所有缓存并关闭连接。


执行存储、推荐引擎、API、移动端一致性、serve snapshot 和 outbox 回归：**955 passed**（199.58s）。全量 `ruff check src/ tests/` 与基准脚本检查通过。`mypy src/` 仍有基线已有的 10 项错误，分布在 `image_service.py`、`worker/main.py`、`api/app.py`；本次改动无新增错误。

## 真实 HTTP / WebSocket / SQLite 验证

原配置、原数据库、完整后台 worker 和推荐子进程运行优化分支，待启动就绪后执行一次真实 `reshuffle`。返回 6 条推荐，HTTP 耗时 **689.9ms**；推荐 ID 和 shown 状态已落库，无批内重复。响应的剩余总量与各来源之和一致，同版本 WebSocket 库存匹配，随后 GET 库存也一致。并发健康探测 6 次，最大 21.6ms；验证失败列表为空。[原始聚合结果](results/recommendation-reuse-live.json)。

真实后台持续补池，测试前库存 6 条，出批 6 条后库存为 3 条，不应以简单减法判断并发期间的库存；验证使用响应已提交库存及推送/查询一致性。此次库存较少，仅是单次完整请求的功能与耗时样本，不能据此推断大库存、高并发或手机网络下的 p95，也没有同条件线上前后对照。服务重启初期曾出现推荐子进程尚未就绪的 502，稳定后再执行上述验收。
