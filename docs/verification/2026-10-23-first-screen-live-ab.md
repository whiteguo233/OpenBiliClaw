# 首屏再次优化：服务事件循环与脚本请求（2026-10-23）

## 结论与范围

相对上一轮修复 `733f69dc`，本轮六次交替启动真实 API、十二次真实浏览器导航中，冷封面前四张完成中位数从 **2020 ms 降到 1274 ms（约 37%）**，热封面从 **849 ms 降到 598 ms（约 30%）**。每次导航八张图片全部成功，浏览器脚本异常为零。当前结果来自本机隔离验收，尚未合入 main 或部署到用户 Windows 电脑，不能直接当作用户机器的实测结果。

没有降低画质、删除功能或将图片请求替换为 mock。推荐内容固定为现有缓存中的同八条真实记录；图片经真实 `/api/image-proxy` 下载。页面仍会按原逻辑探测实际配置的模型服务。验收环境没有 B 站 Cookie，关闭小鱼循环，没有发布评论或私信。

## 诊断证据

对旧版首次导航做服务端 CPU 采样和事件循环心跳采样，发现约 **1191 ms** 的最长事件循环延迟。调用链为 `init_prereqs.chat_ready → probe_chat_provider → OpenAIProvider → AsyncOpenAI.chat`；SDK 第一次惰性导入资源及构建模型类型在 HTTP 主线程执行，单是 `chat` 属性解析约 **1126 ms**。同时正在下载的图片和健康请求一起等待。

同次采样中，八张真实图片上游下载中位数约 **338 ms**，磁盘查询约 **6 ms**，落盘约 **7 ms**。因此本轮没有继续改磁盘缓存索引或 fsync，也没有把主要卡顿归因于 CDN。另一个代码路径是健康接口同步执行网卡命令；本机不是这次最大的耗时点，但慢命令的并发 HTTP 回归能确定性复现它阻塞 ping。

修复后，同样的诊断采样最长事件循环延迟降至约 **87 ms**，前四图从 **3013 ms** 降到 **1668 ms**。采样有额外开销，这组数字仅用于归因；正式效果采用下一节无采样的数据。

## 实现

- Chat Completions / Responses 的 SDK 惰性资源解析用 `asyncio.to_thread` 执行；实际网络请求和流消费仍在调用者事件循环，重试、凭据、模型路由不变。
- `/api/health` 的网卡探测移到工作线程；锁合并并发冷查询，保留 30 秒缓存。二维码仍每次重新探测，并按序发布新地址；失败不缓存。
- 新增 API 内部 `DesktopAssets`：固定清单中的 12 个桌面脚本按原顺序拼接为一个 defer 请求，首次构建一次性 gzip，最多保留两个内容版本。HTML、全部脚本及三个样式表参与版本计算。原始脚本路径继续服务其它客户端和开发工具，无 Node 构建或安装步骤变化。
- 带版本 URL 只返回对应内容，过期版本 404；编码协商、表示独立 ETag、304、密码门禁均有回归。三个桌面 HTML 入口行为一致。

## 正式真实请求 A/B

Chromium 151，1440 × 1000；基线工作树 `733f69dc`，候选 `fix/web-first-screen`。次序为 **旧、新、新、旧、旧、新**，每轮独立启动 API 进程、使用同一份八条记录的隔离 SQLite 副本，图片目录从空开始。先冷导航，再在该进程热导航。每次都禁用浏览器 HTTP 缓存，因此热结果表示服务端封面缓存收益，不依赖浏览器本地图片缓存。

计时起点为页面导航；卡片指标表示八条固定验收内容完成建卡，首四图指标要求前四张图片均已加载且 naturalWidth > 0。随后滚动末卡并等待八图完成。整套页面运行原始 API 与后台水合请求，没有拦截响应。性能采样器、pytest 和 MyPy 在正式测量期间未运行。
