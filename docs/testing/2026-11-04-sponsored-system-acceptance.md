# 免费模型全系统业务验收（2026-11-04）

## 判定

**主要功能可以执行，尚不满足“所有基础功能稳定可用”的验收条件。** 两个模型都完成了建像、行为入库、文本向量、搜索、候选评估、推荐文案、反馈学习和真实流式聊天；完整后台负载下仍有批量评估超时、聊天排队和配置应用等待。模型输出也存在指令遗漏与无依据的内容扩写。不能用连接测试成功或单元测试通过替代这些结果。

测试使用公开发行的 [Rust SDK 2026-11-04.1](https://github.com/whiteguo233/OpenBiliClaw/releases/tag/sponsored-runtime-2026-11-04.1)，通过 Core → 签名 IPC → Rust → 硅基流动真实执行，没有注入 API Key，没有模型或业务 mock。两个隔离目录各自保存配置和 SQLite 数据；禁用另一个免费模型及用户付费模型回退，核对调用账本中的实际 provider/model。主工作区和真实用户数据未作为测试输入。

基础数据为 12 条合成行为（编程与阳台种植）、12 条受控候选（8 条编程、2 条园艺、2 条无关内容）。另外执行匿名 B 站真实搜索和完整后台抓取；手机端最终展示了两条真实公开视频。未使用用户账号 Cookie，登录导入、外部平台收藏同步、图片理解、图片向量不在本轮验证范围；未打满 128K/256K 上下文，也未做多用户压测。

## 问题归类

1. **后台与聊天等待**：8B 两轮聊天首段分别等了 43.7 秒、85.1 秒；4B 原两轮分别用时 24.4 秒、86.0 秒。另一次 4B 短句计时首段 27.3 秒，收到 8 个分片，总耗时 27.7 秒。短回复在开始输出后很快完成，延迟不能全部归因于输出速度。当前同一免费 Provider 的 Rust 子进程串行处理请求，后台长调用会占用通道；维护流量还有空池准入等待。日志能确认排队，不能精确分离每次服务端排队和模型推理耗时。
2. **长批次稳定性**：4B 完整后台的候选评估至少两次报 `sponsored runtime timed out`，之后部分批次成功并补入两条库存。8B 实际画像归并也有一次超时。关闭思考并不自动解决所有长任务；下一步需要针对真实批次大小、输入/输出量、请求隔离和超时重试分别验证。
3. **归并不是完全不支持**：另用两个近义 Rust 兴趣做独立小样本，旧专用签名契约在 8B/4B 分别 11.9/22.0 秒返回正确 merge。相同小样本改走已有通用结构化契约诊断时分别 20.4/10.3 秒成功。样本小且只有一轮，不能证明预算调整是大任务超时的唯一原因，也没有据此修改生产归并路由。
4. **内容与指令质量**：4B 漏掉要求的第二个工具；8B 工具齐全却没有给出“编程和园艺”两个不同兴趣。4B 的 Rust 借用解释混入“移动所有权”，推荐文案补写了输入未提供的用户经历。觉察输出还有引用批次外事件 ID 的警告，由 Core 降级归因处理。结构、连通性和事实忠实性必须分开验收。
5. **切换的实际含义**：保存返回成功不代表后台已应用。4B 场景已验证热切换成功；8B 负载场景在 30 秒内未完成，测试没有继续等到应用结束，因此结论是“该时限下未通过”，不是永久无法切换。

## 本轮修改

- 通用免费结构化请求在没有显式设置时，8B 在输出额度至少 2048 时使用 low/1024 思考预算，短请求和 4B 关闭思考；普通文本与工具回复默认关闭思考，保留调用方显式选择。修正前，4B 完整建像和 8B 偏好重建曾触发 180 秒超时；修正后的上述建像样本通过。最后补充的小额度保护由 64/1024/2048 三个边界回归验证；8B 实际使用 64-token 输出上限，0.792 秒返回正确 JSON（8 个输出 tokens）。
- Agent 工具对话原来把完整回复缓冲后一次显示；现在转发 Rust SSE 分片，并将可能的工具 JSON 缓冲到终帧解析，避免显示为聊天正文。取消/关闭流会回收进程、释放请求，后续调用可以重新启动。
- 早期 `soul.consolidation` 专用契约保持原签名和行为，本轮没有改动私有 SDK，也未声称归并长任务已经修好。
- 加入可重复执行的真实业务与 HTTP 验收脚本，记录阶段耗时、实际路由和后台警告。出现断言失败或后台错误时以非零状态结束。

修改在 PR336 开发分支；这些新修正还没有进入正式主程序安装包。

## 验收脚本修正及证据边界

初版测试有几处必须单独记录，避免把测试代码的问题归给模型：初始化应使用 CLI 的前台准入上下文；事件 API 在初始化完成后才可接收；对话学习应提交到串行 settlement queue；SSE 文本事件名为 `delta`。已修正脚本。8B 初版直接调用学习函数触发了 worker guard，相关结果不计入完整对话结算通过证据；真实 HTTP 对话的后台学习另行验证。

早期报告只判断归并函数是否抛异常，误将其带 `errors` 的返回值记为 pass；本报告按内部错误判失败。4B 工具测试也由“至少执行 get_profile”收紧为两个指定工具都执行。首次 HTTP 4B 测试没有记到首段时间，但分片计数有效；另一次独立计时提供首段数据。机器摘要明确保留这些修订，不将旧标签直接当总通过率。

重现命令（需联网，会调用获批额度；目录必须为专用测试数据）：

```bash
PYTHONPATH=src python scripts/sponsored_system_acceptance.py \
  --root /tmp/obc-free-8b-test --model Qwen/Qwen3-8B
PYTHONPATH=src python scripts/sponsored_http_acceptance.py \
  --root /tmp/obc-free-8b-test --port 18442
# 4B 使用另一个新目录，并将 model 改为 Qwen/Qwen3.5-4B。
```

第一段使用真实生产组件和 ASGI 请求，不启动全套 lifespan；第二段启动真实 uvicorn/lifespan，与自主后台任务同时运行。认知周期只将合成数据的调度时钟向前推进 13 小时来触发周期，模型调用、数据写入和向量计算保持真实。
