# 免费 Rust SDK 真实并发验收（2026-11-05）

结论：当前接入支持有界并发，但单个 Rust 子进程并不支持请求多路复用。项目使用一个前台子进程、两个后台子进程组成池，真实请求验证了单池3路同时执行；两个应用进程共享账本时达到6路。不能把“同时提交12项任务”理解为“12项同时推理”，也不能据此宣称高并发下稳定。

## 环境和方法

- Core 基线 `f431ab76`，独立 `test/sponsored-concurrency` worktree；生产 Rust SDK `sponsored-runtime-2026-11-05.1`，已验签的 macOS x86_64 bundle manifest SHA-256 `9c4f6dad43996b9882d54da4eb82412335b4eaf55c5bab5a4fca4a27478ec3de`。
- 硅基流动实际8B、4B、BGE-M3请求。合成提示与隔离目录，无用户历史/Key导出，无模型结果替换。关闭自有模型和另一免费模型回退，以免将替代模型的结果记给被测模型；这也意味着不是默认互备设置的成功率评估。
- 主矩阵通过实际 `LLMService` 准入控制和 `shared_sponsored_provider()` 进入正式工作池；单进程对照直接调用一个 `SponsoredProvider`。向量通过同一池执行真实 `embedding()`，验证1024维、有限、非全零。
- 每条聊天和结构化请求使用唯一标识；检查模型、标识、候选ID、合法JSON及流式终帧与分片一致。只在实际IPC写入/读出函数外观察时间、请求ID和子进程PID，不改变输入、输出、队列或超时。并发峰值指已经写给不同Rust进程、尚未结束的请求数量；不是供应商GPU正在同时执行的可见指标。
- 两模型矩阵部分同时运行，HTTP和跨进程实验亦有部分时间重叠；延迟包含当时账户/网络/上游状态，不能当作模型性能排行榜。本轮没有进行数千用户、持续吞吐或供应商上限压测。

原始记录及派生统计：[results.json](assets/sponsored-concurrency/results.json)。

## 当前实际限制

| 层次 | 行为 |
| --- | --- |
| 单个Rust进程 | 同步读取一帧、执行完再读下一帧；一个Python Provider的请求锁也保证一次一项。 |
| 一个共享工作池 | 固定3个子进程：交互1个，后台/向量2个。只来聊天时峰值1，只来后台/向量时最多2；两类通道不互相借用。 |
| 应用LLM准入 | 默认总并发3、后台2。`LLMService` 使用真实准入门控；直接向量入口不经过该服务gate，但仍受池内两个后台子进程约束。 |
| 聊天HTTP接口 | `DialogueExecutionCoordinator` 另有应用级串行执行租约，跨会话也串行。等候过久时SSE可以先返回“通道正忙”，已保存任务由durable worker继续处理。 |
| 多进程/多池 | 池和gate不是账户全局并发上限；独立应用进程可各持有一个池。共同账本只在短事务中上锁，不在网络请求期间持锁。 |
| 提高配置并发 | `llm.concurrency` 调高不会扩容固定3子进程的免费工作池；需要改变池配置和调度实现才能获得更高的单池实际并行度。 |

所测签名策略的本地安装账本限制为300 RPM、每日20,000请求/20,000,000 tokens、每月300,000,000 tokens。这是客户端策略，不是本轮测得的硅基流动账户限额，也不是并发数；多台安装共用Key仍受服务商账户的统一限制。

## 同时提交的实测结果

除单子进程对照外，均为真实服务gate＋免费池；混合任务含聊天、4候选JSON评估和BGE-M3（3项一组为两项评估＋一项聊天）。

| 场景 | Qwen3-8B：通过/提交；整批耗时 | Qwen3.5-4B：通过/提交；整批耗时 | 实际峰值 |
| --- | --- | --- | --- |
| 同一子进程，3请求 | 3/3；11.06秒 | 3/3；116.48秒 | 1 |
| 工作池，3混合请求 | 3/3；35.81秒 | 2/3；54.97秒 | 3 |
| 工作池，3条聊天 | 2/3；35.46秒 | 2/3；84.21秒 | 1 |
| 工作池，6混合请求 | 5/6；32.85秒 | 6/6；65.87秒 | 3 |
| 工作池，12混合请求 | 9/12；94.50秒 | 11/12；259.99秒 | 3 |
| 取消流后再发聊天/评估/向量 | 3/3；45.57秒 | 3/3；34.49秒 | 3 |

主矩阵两模型各30项正常请求：8B为25通过/5失败，4B为27通过/3失败。另各1项收到真实流式分片后主动关闭，随后均能再次聊天、评估及取得向量；取消的交互子进程被替换，工作位没有泄漏。

8项失败全部为 `SponsoredUnavailableError: sponsored first output timed out`，并非串包、错误请求ID、非法JSON或账本错误。没有观察到429、鉴权拒绝或额度不足响应；这不排除供应商内部排队。成功内容只通过本次标识/格式校验，不是完整业务语义质量认证。

### 排队与执行耗时

- 8B三混合场景中，两项后台评估仍在执行时，聊天0.751秒出现首段，3.626秒完成，证明前台保留通道实际可用。
- 12项同时进入时，本地等待写入IPC的最长时间：8B **63.537秒**，4B **93.150秒**。4B最后一项评估总耗时259.917秒，其中排队93.089秒，写给Rust之后约166.828秒。
- 向量服务本身很快也可能排队：8B六项场景一项向量总耗时28.201秒，其中排队27.772秒；4B十二项场景一项向量总耗时40.795秒，其中排队40.598秒。当前向量与后台长评估共享两条通道。
- 30秒首段预算从取得Rust通道后开始，不涵盖此前所有排队。4B十二项场景最后一条成功聊天在提交后120.815秒才出现首段，前面已排队93.150秒。180秒请求预算也不是端到端总等待上限。
- 仅凭IPC时间不能进一步区分Rust内余额探测、网络和服务商内部排队。本轮证明了慢等待发生在哪个边界，没有把所有等待武断归因于模型算力或云端限流。

## 真实HTTP与多个应用进程

真实uvicorn/TCP服务同时执行两条不同会话的Agent SSE聊天、两项评估、两项向量；持续探测 `/api/ping`，并核对数据库中的最终回复。

| 场景 | 结果 |
| --- | --- |
| 8B HTTP六项 | 两评估、两向量成功。第一条聊天首段超时并落为failed；第二条SSE先返回通道忙，但durable worker随后实际完成，标识正确、回复落库。因此SSE当次4/6通过，最终业务完成5/6，不能把忙提示记为永久丢失，也不能把第一条超时改成成功。 |
| 4B HTTP六项 | 6/6通过，两聊天均completed且数据库回复匹配。首段分别16.306/32.927秒，总耗时17.437/34.638秒；第二条包含聊天租约排队。 |
| API响应性 | 8B场景74/74次ping成功，P95 5.0ms，最大71ms；4B场景69/69成功，P95 5.4ms，最大113ms。模型等待没有阻塞整个API事件循环。 |
| 两Python应用进程，共享同一账本 | 每个进程各提交两评估＋聊天＋向量，合计8/8通过，重叠窗口实际有6个Rust进程持有请求。账本记录8请求，任务计数总和也是8；没有锁竞争、MAC或generation错误。 |

8B首轮HTTP观测器对无终帧的超时请求直到关服才结束计时间隔，原记录因此误算峰值4。以HTTP错误实际返回时间收敛该中断区间后为3；原始值、区间和修正说明均保留于JSON。后续HTTP观测器在错误返回时及时结束该区间；主要并发结论由独立SDK矩阵和跨进程数据验证。8B最终任务状态另外在正常关服后读取隔离数据库确认；4B实验在关服前轮询了最终状态。

## 判断与下一步

支持项目内受控的后台并行和前台保留，但当前不满足“多路聊天立即并发响应”或“12路同时推理”的预期。单纯提高 `llm.concurrency` 不能解决固定工作池瓶颈，也不能消除写入Rust后的慢响应。

如果下一步要提高吞吐，先处理前台/后台空闲槽不能借用、向量被长评估阻塞、端到端排队预算和忙状态展示，再评估可配置工作池及账户级限流。聊天执行租约还保护对话写入与热重载，不能为了增加并发直接删锁。此次只测试和记录，没有扩大生产并发、改提示/超时或发布新Rust组件。

并发与取消相关离线回归：106 passed。上一提交 `f431ab76` 的11项CI已全部通过；本轮仅增加验收脚本和文档，没有重复此前一小时全项目测试。真实失败原样保留，不以离线回归通过替代服务稳定性。

## 复验

使用新目录，`--bundle` 指向已验签的正式bundle，可省略以走正式安装入口。调用不需要在命令或配置中填写共享Key。

```bash
PYTHONPATH=src python scripts/sponsored_concurrency_acceptance.py \
  --root /tmp/obc-concurrency-8b --model Qwen/Qwen3-8B
# 将模型改为 Qwen/Qwen3.5-4B，并使用另一新目录。

PYTHONPATH=src python scripts/sponsored_http_concurrency_acceptance.py \
  --root /tmp/obc-concurrency-http --model Qwen/Qwen3-8B \
  --bundle /absolute/path/to/verified/bundle
```

跨进程复验同时启动两个第一类脚本，分别使用不同 `--root`，并传入相同的 `--ledger /tmp/obc-concurrency-ledger --scenario process-worker`。只使用测试目录，避免混入用户账本。结果保存为各目录的 `concurrency.json`，失败返回非零。
