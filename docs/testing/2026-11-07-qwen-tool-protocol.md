# 免费 Qwen 工具链的进一步修复与实测（2026-11-07）

在 `feat/unified-sponsored-providers`、`9464bb88` 基线上继续处理[上一轮](2026-11-07-tool-text-guard.md)留下的重复读取、示例误执行和虚假完成声明。改动位于公共仓库的 Python AgentLoop 与免费适配器。测试使用已签名 Rust SDK、硅基流动真实请求、临时配置/数据库/钥匙串账户；未改用户正式配置，未使用付费备用模型，也未发布安装包。

## 定位与实现

1. **工具返回后重复了原始“先读取”指令。** 捕获的请求在实际 `read_memory` 结果之后又附加完整用户请求，容易让模型重复第一步。移除这一重复指令，保留调用 ID、工具名和 JSON 编码的实际结果，明确空画像也代表读取完成。
2. **原来的裸 JSON 动作协议与用户索要的 JSON 数据混淆。** 改用 Qwen 的 `<tool_call>` / `<tool_response>` 标记。普通 JSON/代码直接作为正文，不再通过 `reply` 字符串封套绕行。这个协议在已签名的文本调用内实现，**不是上游 HTTP 原生 function calling**；发行 SDK 的字段白名单与消息角色限制保持原样。[Qwen 官方模板](https://huggingface.co/Qwen/Qwen3-8B/commit/895c8d171bc03c30e113cd7a28c02494b5e068b7)、[硅基流动 function calling 文档](https://docs.siliconflow.com/en/userguide/guides/function-calling)。
3. **明确点名调用却没有执行记录。** 一次真实 4B 返回“我已读取核心记忆……信息已足够”，实际零工具调用。对直接点名已注册工具的调用指令，先暂存尚无执行记录的正文，最多纠正一次；仍无调用则失败，避免显示、保存和学习假成功。普通提问、条件句、代码示例和引用不产生这种要求；失败调用或审批登记也算一次尝试，不自动重放写操作。
4. **正确调用带了一句说明也被拒绝。** 后续删除审批测试捕获了“好的，我先读取……\n\n<tool_call>...”这种合法意图。仅接受起始标记过于严格，追加格式提示也不稳定。现在按行和代码围栏识别完整动作后缀，说明前缀交给 AgentLoop 作为进展；围栏、缩进、引用、行内示例及普通 JSON 保持数据。动作仍须通过名称、参数、完整后缀和原审批门校验。
5. **审批调用参数复制了整个 JSON，而非笔记 value。** 实际捕获到 4B 把整段转义后的笔记读取结果放入 `expected_value`。JSON 对象/数组现在直接呈现其字段，保持内部字符串原值不变；若已经拿到工具结果却仍漏掉明确要求的步骤，一次纠正只提供尚未调用的明确工具 schema。初始工具集、执行参数校验、CAS 与审批门保持原样，系统不会替模型填写或改写操作参数。

保留上一轮的相同读取收敛、真实错误原因识别和有限持久重试。只有显式配置的实例链可以换模型，已输出或执行工具后不重跑整个任务。

## 有对照的真实协议实验

同一组捕获请求，通过安装的签名 SDK 发起真实上游调用。每格 3 次，小样本只能证明问题和方向，不代表总体成功率。

| 模型 / 阶段 | 旧协议 | 仅移除重复原指令 | 强制 kind/type JSON 封套 |
| --- | ---: | ---: | ---: |
| 8B：已获得读取结果后收尾 | 0/3 | 3/3 | 0/3 |
| 4B：已获得读取结果后收尾 | 3/3 | 3/3 | 1/3 |
| 8B：初始工具选择 | 3/3 | 3/3 | 3/3 |
| 4B：初始工具选择 | 3/3 | 1/3 | 3/3 |

共 54 次请求（另含展示 JSON 压力场景）。typed 封套使解析更差，未采用。4B 初始请求在前两组实际上相同，差异说明模型/服务波动，不能归因为删除了后续指令。压力场景含固定 skill 与用户输出格式冲突，不把其精确字符串失败率当日常任务能力分数。

随后 24 次 Qwen 标记格式试验：4B 初次调用和结果收尾各 3/3；8B 分别 2/3、1/3，三个失败均为无输出超时。普通 JSON 示例的精确字符串保真 4B 为 1/3，8B 为 3/3；4B 另两次加了说明/围栏，均没有执行示例。所有失败保留在配套 JSON 中。

审批补测额外进行了 18 次输出格式对照，发现只追加“仅输出标记”或“审批须调用”提示仍会返回说明文字加调用，因而先修复解析器。另做 12 次参数对照（相同读取结果与纠正上下文，每组 3 次）：

| 策略 | 发出正确 delete_memory 且 expected_value 完全匹配 |
| --- | ---: |
| 完整工具集、结果为转义字符串 | 0/3 |
| 仅保留结果对象结构 | 2/3 |
| 仅聚焦剩余明确工具 | 2/3 |
| 两项结合 | 3/3 |

前述共 108 次协议实验均保留逐项结果；参数对照只生成调用而不执行删除，不能替代后面的真实审批执行验收。

## 真实 API 与页面流程

- 从空链在真实 `/setup/` 页面选择 4B、8B 和 BGE-M3，所选模型成为默认链第一项；保存、配置回读、LLM 与 embedding 探针成功。
- 第一版标记桥接复测：4B 读取 2/3，另一次就是上述假完成；8B 读取 2/3，另一次超时；显式 8B→4B 链 3/3，使用账本确认一次落到 4B。该阶段失败没有删除。
- 加上执行记录检查后的主复测：4B 五次读取均完成（1.850–5.934 秒），8B 三次均最终完成（3.836–57.328 秒）。8B 一次原始 SSE 返回可重试错误，后台重试后 durable turn 完成；**不能算三次都在首条流上成功**。每次实际读取一次，空画像结论正确。
- 同阶段显式 8B→4B 链三次完成（2.796–14.183 秒），本组账本仅出现 8B，因此这组验证配置链可用，实际切换证据来自上一阶段。
- 两模型展示 JSON 都没有触发操作，JSON 内容均保留；8B 字符串精确一致，4B 加了说明和围栏，精确格式仍未满足。
- 实际笔记写入后读取通过，并核对 `tool_result` 与临时记忆文件；审批测试另外核对真实审批卡、待批准记录以及批准前笔记仍存在。

最后补测在两个模型各自的**单模型链**中，各独立启动两次空环境，实际执行完整流程：

| 模型 | 笔记写入并读回 | 正确审批参数及待办 | 批准后删除 / 再次批准不重放 | 读写对话耗时 | 审批对话耗时 |
| --- | ---: | ---: | ---: | --- | --- |
| Qwen3.5-4B | 2/2 | 2/2 | 2/2 | 3.914–7.032 秒 | 4.029–6.980 秒 |
| Qwen3-8B | 2/2 | 2/2 | 2/2 | 12.349–29.360 秒 | 42.158–53.422 秒 |

同时核对审批参数 `expected_value` 与磁盘 value 精确相同、批准前笔记存在、批准后从
`agent_notes` 消失，以及审批接口返回 `executed`；再次批准返回 `already_executed`。
各环境使用账本中只出现所选模型，没有借助另一免费模型或付费模型完成上述四轮。
这些对话中工具执行各一次。此前失败、错误参数和未生成审批卡的样本同样保留在 JSON。

## 能力与交付边界

- 这次修复的是接入协议、工具结果续接和可核实的执行状态；没有提升模型权重本身的推理能力。
- 8B 仍有首输出超时和几十秒等待；4B 仍可能增加不要求的说明/围栏。请求恢复成功不意味着延迟已经解决。
- 明确工具名检查不从“帮我看看”之类普通中文猜测操作，不验证参数语义或最终回答的全部事实，不能保证所有长任务正确。
- 此轮没有修改签名/凭据/配额/配置字段、前端表单或安装器。PC/移动/插件/CLI 共用后端接口，沿用上一轮四端验收；本轮新增真实浏览器范围为初始化，核心工具和审批走真实 HTTP/SSE。不会把 synthetic IPC UI 回归称作真实模型请求。
- 临时服务、测试数据和对应钥匙串 ledger 均由各脚本清理。没有把 API Key 或签名策略写入报告。当前工作仍在开发分支，等待随主应用集成发布。
